# solution-writing-standard

正式交付型方案 / 实施方案的编写、改稿、评审与交付自检 Skill。

## 这是什么

一个把「方案怎么写、怎么改、交付前怎么查」固化成条款的 Skill：以《方案编写通用规范》为唯一依据，配一套可直接套用的交付模板，以及一份术语清理与去 AI 味的操作指引。

适用对象是需要提交评审、试点或验收的方案类文档——实施方案、建设方案、落地方案、标准规范说明等。规范条目来自多次真实方案的编写、评审与改稿复盘，与具体业务领域无关。

## 能力

- **三种工作模式**，按任务自动选路：
  - 新写方案：定读者与边界 → 摆依据 → 套骨架 → 写术语 → 落实施 → 收待确认 → 加表达层 → 排期克制
  - 改稿修编：留快照 → 出施工总图 → 确认后动正文 → 逐处对照 → 留痕升版 → 抽检验证
  - 交付前自检：按附录 A 的 5 组清单（边界与依据 / 结构与表达 / 落地与门禁 / 评审与版本 / 格式与验收）逐项出报告
- **《方案编写通用规范》**：10 类规范条款 + 附录 A 自检清单 35 项，覆盖定位与边界、结构、依据、术语、落地、读者与表达、评审与迭代、版本管理、格式与交付、沉淀与复用
- **交付模板集**：文档控制表、本版变化表、修订施工总图、待确认事项表、角色 RACI、评审问题登记表、一页导读、术语表三列制，共 8 套骨架，直接套用
- **术语与去 AI 味**：语料分级与命中率判定、五步清理流程、可复用的脚本骨架与三重验证（旧词零残留 / 新词就位 / 结构不变）、常见误杀保留参考、页数压缩三轮法、判定规则去打分化改法
- **硬约束内置**：禁止虚构依据与修订记录；不承诺工期；口径修改与通俗化翻译分两条线；覆盖已有文件前先确认并留改前版

## 安装

把本仓库内容放入 OpenCode / DeepWorks 的 skills 目录：

```
<项目根>/.opencode/skills/solution-writing-standard/
```

无脚本依赖，纯 Markdown，任何支持 Skill 目录约定的环境都可用。

## 用法

按任务选模式，或直接说触发语：

| 你要做什么 | 说一句 | 走哪个模式 |
| --- | --- | --- |
| 从零写一份方案 | 「帮我新写一份实施方案，先给我施工骨架和待确认清单」 | 模式 A |
| 按评审意见改稿 | 「这是评审意见（附件），先出施工总图给我确认，不要直接改正文」 | 模式 B |
| 术语与 AI 味清理 | 「方案要交了，把术语和 AI 味过一遍，先出对照表给我确认再改」 | 模式 B ＋ 操作指引五步流程 |
| 交付前过清单 | 「方案要交付了，按规范把自检清单过一遍，给我逐项报告」 | 模式 C |

模式 B 的门禁是硬的：没有确认过的施工总图，不动正文；交付的必须是可直接粘贴的成品文字，不是方向性建议。

## 边界

- 只做编写、改稿与自检，不代签评审结论，不替使用者做业务判断。
- 规范条款针对文档方法与流程，具体业务内容（名称、责任人、数据、系统配置）须由执行方确认，不由本 Skill 假定。
- 覆盖已有交付文件前必须先获得确认，并保留改前版本。

## 版本与维护

当前版本 **v1.2.0**，以 `SKILL.md` 的 `metadata.version` 为准。

- **升版规则**（沿用《方案编写通用规范》八.3）：定义、边界、类型、责任发生影响兼容性变化时升主版本；补充说明或非语义调整时升次版本。
- **修订流程**（沿用规范七.1、七.9）：先出施工总图，确认后才动正文；任何一轮大改前先留改前快照，支持对比与回退。
- **版本号同改**：`metadata.version`、本文件与变更说明须同步修改，避免同一仓库出现多个版本号。
- **不设文档控制表**：本仓库是 Skill 源码而非交付文档，版本变化以 `metadata.version` 与提交历史为准；提交信息写明「改了什么」与「为什么改」。
- **内容边界**：条款只针对文档方法与流程，不承载具体业务内容、具体使用者信息与具体系统配置。
